Encoding Techniques Theory

Implementation, security analysis, and possible attacks related to encoding in AcadPortal.

Encoding & Decoding Implementation

This project uses Base64 encoding (RFC 4648) — a technique that converts binary or text data into a set of 64 printable ASCII characters (A-Z, a-z, 0-9, +, /).

Where Base64 is Used

Feature Encoding Process Decoding Process
Export Encoded Profile Student profile JSON → base64.b64encode() → downloadable .txt file Base64 string → base64.b64decode() → original JSON data
PEM Key Files Binary encryption/signing keys → Base64-encoded body → wrapped with -----BEGIN/END----- headers PEM file → strip headers → base64.b64decode() → raw binary key

Encoding / Decoding Example

Encoding:
Input: {"full_name": "John Doe", "cgpa": 7.2}
→ UTF-8 bytes → base64.b64encode()
Output: eyJmdWxsX25hbWUiOiAiSm9obiBEb2UiLCAiY2dwYSI6IDcuMn0=

Decoding:
Input: eyJmdWxsX25hbWUiOi...
→ base64.b64decode() → UTF-8 decode
Output: {"full_name": "John Doe", "cgpa": 7.2}

Implementation files: utils/crypto.py → encode_base64() and decode_base64() functions; _read_pem() and _write_pem() for PEM key handling.

Security Levels & Risks (Theory)

CRITICAL: Encoding is NOT Encryption. Anyone can decode Base64 without any key — it provides zero confidentiality.

Security Level Assessment

CIA Property Level Explanation
Confidentiality None Base64 is a public algorithm. Any encoded string can be decoded instantly using tools like atob(), online decoders, or command-line utilities. No secret key is needed.
Integrity None Encoding does not include checksums, MACs, or any mechanism to detect if data has been modified in transit.
Availability / Compatibility High Base64 ensures binary data can safely travel through text-only protocols (HTTP headers, SMTP, URLs, JSON) without corruption.

Associated Risks

  1. False Sense of Security: Developers may mistake encoded data (e.g., dXNlcjpwYXNz) for encrypted data because it "looks random." This leads to exposing passwords, PII, or API keys that are merely encoded, not protected.
  2. Data Bloat: Base64 increases data size by approximately 33% (every 3 bytes becomes 4 characters). This impacts bandwidth, storage, and performance when applied to large files or frequent API calls.
  3. Obfuscation Abuse: Attackers use encoding to bypass Web Application Firewalls (WAFs) and input validation filters that only scan for known plaintext attack patterns like <script> or DROP TABLE.

Mitigation in This Project

  • Sensitive data (marks, risk scores) is protected by AES encryption, not encoding
  • Passwords are stored as PBKDF2-SHA256 salted hashes, never encoded
  • Base64 is used only for data formatting (profile export, PEM key files) — never as a security control

Possible Attacks (Theory)

1. Decoding Sensitive Information

Scenario: An attacker intercepts network traffic or inspects browser local storage and finds a "secure token": dXNlcm5hbWU6cGFzc3dvcmQ=

Attack: The attacker recognizes the Base64 pattern (alphanumeric + = padding) and decodes it instantly

Result: username:password is revealed — complete credential compromise

Countermeasure: Never use encoding for credentials. Use encrypted tokens (JWT with signing) or session-based auth (as implemented in this project).

2. WAF/Filter Evasion via Encoding (XSS)

Scenario: A web application blocks <script> tags in user input to prevent XSS attacks

Attack: The attacker submits a Base64-encoded payload instead:

eval(atob('YWxlcnQoJ1hTUycp'))

Result: The browser executes alert('XSS') — the filter was bypassed because it only checked for plain <script>

Countermeasure: Validate and sanitize decoded input, not just raw input. Use output encoding (Jinja2 auto-escapes by default in this project).

3. Forced Browsing / IDOR with Encoded IDs

Scenario: A web application uses Base64-encoded user IDs in URLs: /profile/MQ==

Attack: Attacker decodes MQ== → 1, then encodes 2 → Mg==, and accesses /profile/Mg==

Result: Unauthorized access to another user's profile — trivial enumeration because encoding is reversible without a key

Countermeasure: Use server-side session checks (this project uses current_user.id from Flask-Login, not URL parameters).
